# Guarantee Ledger

このリポが外へ約束している振る舞いと、それを守るテストの一覧である。約束が破れればテストが落ちるので、
ここに書いたことは気づかないうちに実装とずれていかない。**ここに載っていない振る舞いは約束ではなく、予告なく変わりうる。**
対象は、`python -m tg_dev_digest` の引数と終了コード、1回の実行で何を送り何を覚えるか、`digest.toml` と環境変数の解釈、Telegram に届くメッセージの形、`type = "feed"` で読めるフィードの形式である。選別モデルの応答の解釈や配信元ごとの HTML・API の解析といった補助の関数と、`worker/`・`.github/workflows/` は対象外とする。地位は設計判断の文書（`context/`）と同格。

- 目的: いま何を約束しているかを1か所で読む。変更の前に、破ってはいけない約束をここから引く。テストの無い約束を Gaps に残す
- 分け方: 約束の対象（CLI・1回の実行・設定・メッセージ・フィード）ごとに1ファイル。テストファイルや Issue の単位では分けない。新しい対象を作ったときだけファイルを足す
- 書き方: 各ファイルに「保証｜対応テスト」の表を置き、1行に約束を1つ、宣言文で書く。出典・経緯・設計の理由は書かない（`CLAUDE.md` と `context/` が持つ）。実データでの目視確認と開発用の検査は載せない。約束が10行以上のファイルは、何についての約束かで `##` の見出しを立て、見出しごとに3行以上の表を置く。3行に満たないまとまりは近い見出しにまとめ、10行未満のファイルは見出しを置かない。見出しは行の主語になる名詞句にする。ファイルは分けず、行を足して10行以上にした変更が同じ変更の中で見出しを立てる
- 引き方: Issue で「維持する保証」を挙げるときは、変更の対象のファイルを開く。テストが落ちたら、テストの名前で台帳を検索すると、破れた約束の行が見つかる。約束が守られていることは、全テストを流す CI が確かめる。コードのファイルから約束を引く仕組みは置かない（実装とテストの名前は1対1でなく、機械では正確に引けない）
- 運用: 変更の前にこの README を読み、変更が触れるファイルから「維持する保証」を引く。約束を足す・変える・消すときは、承認を受けた保証節の文のまま、該当するファイルの表に行を足す・直す・消し、対応テストも同じ変更で直す。Issue や作業ごとにファイルや節を起こさない。テストの無い約束は Gaps に書き、テストを足したら表へ移す。乖離は `guarantee-audit` で棚卸しする
